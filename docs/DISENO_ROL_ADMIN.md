# Diseño — Rol Administrador de plataforma

**Fecha:** 2026-06-20 · **Estado:** propuesta (sin código) · **Autor:** sesión Claude Code
**Objetivo:** introducir un tercer actor —el **administrador de plataforma**— que gobierne
todos los negocios (tenants), distinto del *dueño* (un negocio) y del *apoderado* (cliente).

> Esto es lo que separa a ReservaKids de un SaaS de juguete: un plano de control de
> plataforma (altas/bajas de negocios, soporte, métricas globales). No es una "red social";
> es la consola del operador del producto.

---

## §1 Contexto: el modelo de actores hoy

Verificado en el código (2026-06-20):

| Actor | Entidad | Auth | `rol` JWT | tenant | Rutas |
|---|---|---|---|---|---|
| Dueño | `Usuario` (`tenant_id NOT NULL`) | `AuthService` | `DUENO` | sí | `/api/**` |
| Apoderado | `CuentaCliente` (entidad separada) | `ClienteAuthService` | `CLIENTE` | **no** | `/api/cliente/**` |
| **Admin** | **— (falta) —** | **— (falta) —** | **`ADMIN`** | **no** | **`/api/admin/**`** |

Piezas reutilizables ya presentes:
- `JwtService` emite tokens HS256 con `iss/aud/exp`; ya tiene un método **sin tenant**
  (`emitirAccessTokenCliente`) → patrón directo para `emitirAccessTokenAdmin`.
- `JwtAuthFilter` mapea `rol` → `ROLE_<rol>`: con `rol=ADMIN` sale `ROLE_ADMIN` **sin tocar el filtro**.
- `RefreshCookieService` ya soporta múltiples cookies (`COOKIE_DUENO=rk_refresh`,
  `COOKIE_CLIENTE=rk_cliente_refresh`) → se añade `COOKIE_ADMIN=rk_admin_refresh`.
- `Tenant` ya tiene `estado` (`ACTIVO`/`SUSPENDIDO`/`CERRADO`) con semántica de offboarding
  → **suspender/reactivar ya es modelable**, solo falta exponerlo a un admin.
- `AuthPrincipal(usuarioId, tenantId, rol)`: para admin, `tenantId=null` (igual que cliente).

---

## §2 Decisión arquitectónica: entidad `Administrador` separada

**Elegido:** una entidad/tabla `administrador` independiente, con su propio servicio de auth,
**replicando el patrón de `CuentaCliente`** (que ya es un actor con auth separada y sin tenant).

### Alternativas evaluadas

| Opción | Pros | Contras | Veredicto |
|---|---|---|---|
| **A. Entidad separada** (elegida) | Preserva `Usuario.tenant_id NOT NULL` (invariante más valiosa del proyecto, según la auditoría); blast radius aislado; coherente con `CuentaCliente`; un bug de admin no toca login de dueños/clientes | Algo de duplicación de auth (mitigable: misma `TokenPort`, mismo `PasswordEncoder`, mismo `RefreshCookieService`) | ✅ |
| B. Reusar `Usuario` con `tenant_id` nullable + `rol=ADMIN` | Menos clases | **Rompe** `tenant_id NOT NULL`; mezcla plano de control con datos de negocio; toda query que asume tenant del usuario se vuelve insegura por defecto | ❌ |
| C. `rol=ADMIN` en `Usuario` apuntando a un tenant "sistema" (id 0) | No cambia el esquema | Tenant fantasma contamina listados, métricas, slugs; hack frágil | ❌ |

**Justificación:** el proyecto ya pagó el costo de separar `CuentaCliente`; aplicar el mismo
patrón es la opción de menor sorpresa y mayor seguridad. La duplicación se acota compartiendo
infraestructura (token, hash, cookie, SHA-256).

## §3 Modelo de datos — migración Flyway `V18`

```sql
-- V18: rol administrador de plataforma (gobierno de negocios cross-tenant).
--
-- Actor separado de usuario (dueño) y cuenta_cliente (apoderado): NO tiene tenant_id.
-- Auth propia, replicando el modelo seguro de refresh con rotación (V16).

CREATE TABLE administrador (
    id            BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    email         VARCHAR(255) NOT NULL UNIQUE,
    password_hash VARCHAR(255) NOT NULL,
    nombre        VARCHAR(255) NOT NULL,
    creado_en     TIMESTAMPTZ  NOT NULL DEFAULT now()
);

CREATE TABLE refresh_token_admin (
    id              UUID PRIMARY KEY,
    administrador_id BIGINT     NOT NULL REFERENCES administrador(id),
    token_hash      VARCHAR(64) NOT NULL,
    expira_en       TIMESTAMPTZ NOT NULL,
    revocado        BOOLEAN     NOT NULL DEFAULT FALSE
);
CREATE INDEX ix_refresh_admin_admin ON refresh_token_admin(administrador_id);
```

> **Sin seed en la migración.** El primer admin NO se hornea en el SQL (un hash en el repo es
> deuda de seguridad y queda en el historial git). Ver §4.

### Auditoría de acciones (recomendado, opcional en MVP)
Toda acción sensible de admin (suspender/reactivar/cerrar un negocio) debería dejar traza:

```sql
CREATE TABLE admin_audit_log (
    id              BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    administrador_id BIGINT NOT NULL REFERENCES administrador(id),
    accion          VARCHAR(64) NOT NULL,   -- SUSPENDER_TENANT, REACTIVAR_TENANT, ...
    tenant_id       BIGINT,                 -- objeto afectado (nullable)
    detalle         TEXT,
    creado_en       TIMESTAMPTZ NOT NULL DEFAULT now()
);
```
*(Decisión abierta: incluir en MVP o diferir — ver §10.)*

## §4 Bootstrap del primer administrador (sin huevo-y-gallina)

El primer admin se crea **al arranque, desde variables de entorno**, idempotente y fail-safe:

- `ADMIN_BOOTSTRAP_EMAIL` y `ADMIN_BOOTSTRAP_PASSWORD` (texto plano, solo en el entorno del
  orquestador — Cloud Run `--env-vars-file`, nunca en el repo).
- Un `ApplicationRunner` (`AdminBootstrap`): si ambas vars están presentes **y** no existe ya
  un admin con ese email → crea uno (`passwordEncoder.encode(...)`). Si ya existe, no hace nada.
- Si las vars están vacías → **no crea nada** (no rompe el arranque; igual que `JWT_SECRET`
  vacío en dev degrada con cuidado). En demo/prod se setean una vez y luego pueden quitarse.

Alternativa para rotación/altas posteriores: endpoint `POST /api/admin/administradores`
(solo ADMIN) para que un admin existente cree a otro. *(Diferible post-MVP.)*

## §5 Capa de seguridad

### `SecurityConfig` — nuevas reglas (orden importa, van **antes** de `/api/**`)
```java
.requestMatchers("/api/admin-auth/**").permitAll()          // login/refresh/logout admin
.requestMatchers("/api/admin/**").hasRole("ADMIN")          // consola de plataforma
.requestMatchers("/api/cliente/**").hasRole("CLIENTE")
.requestMatchers("/api/**").hasRole("DUENO")
.anyRequest().denyAll()
```

### `RateLimitFilter`
Añadir `/api/admin-auth/` a `shouldNotFilter` (hoy cubre `/api/auth/` y `/api/cliente-auth/`)
para acotar fuerza bruta contra el login de admin —la cuenta más sensible del sistema.
**Considerar un límite más estricto** para admin (p. ej. 10 req/min) dado el privilegio.

### JWT
`JwtService.emitirAccessTokenAdmin(Long adminId, String email)` → `rol=ADMIN`, **sin** `tenantId`
(copia exacta de `emitirAccessTokenCliente`). `TokenPort` gana ese método.

### Cookie
`RefreshCookieService.COOKIE_ADMIN = "rk_admin_refresh"`, mismo `Path=/api`, HttpOnly+Secure+SameSite.

## §6 Capa de aplicación

- **`AdminAuthService`** (espejo de `ClienteAuthService`): `login`, `refresh` (con rotación y
  revocación de familia ante reuso), `logout`. **Sin auto-registro público** (el admin no se
  registra solo; se bootstrapea por §4). Reset de contraseña: *diferible* (un admin es operación,
  no usuario masivo; se puede rotar por env o por endpoint admin→admin).
- **`AdminService`** (gobierno de negocios, cross-tenant):
  - `listarNegocios(filtro, paginación)` → todos los tenants con estado, plan, nº reservas, fecha.
  - `suspender(tenantId)` / `reactivar(tenantId)` → cambia `Tenant.estado`
    (`SUSPENDIDO` ↔ `ACTIVO`). Reusa la semántica existente; `verificarTenantOperativo`
    de `AuthService` ya bloquea el login de un tenant suspendido. **Quemar refresh tokens del
    tenant suspendido** para expulsar sesiones vivas (no solo bloquear logins nuevos).
  - (Opción "métricas") `metricasGlobales()` → nº negocios por estado, reservas totales,
    señas/ingresos agregados.

## §7 Contratos de API

### Auth (`/api/admin-auth`, público + rate-limited)
| Método | Ruta | Body | Respuesta |
|---|---|---|---|
| POST | `/login` | `{email, password}` | `200 {accessToken, email, nombre}` + cookie `rk_admin_refresh` |
| POST | `/refresh` | cookie | `200 {accessToken, ...}` (rota cookie) |
| POST | `/logout` | cookie | `204` (revoca familia, borra cookie) |

### Consola (`/api/admin`, `ROLE_ADMIN`)
| Método | Ruta | Acción |
|---|---|---|
| GET | `/negocios?estado=&q=&page=` | Listar tenants (paginado, filtrable) |
| GET | `/negocios/{id}` | Detalle de un negocio |
| POST | `/negocios/{id}/suspender` | `ACTIVO → SUSPENDIDO` (+ revoca sesiones del tenant) |
| POST | `/negocios/{id}/reactivar` | `SUSPENDIDO → ACTIVO` |
| GET | `/metricas` *(opción B)* | KPIs globales de plataforma |

## §8 Frontend (Vue 3 + Pinia)

- **Store** `stores/adminAuth.js` (espejo de `auth.js`/`clienteAuth.js`): access token en
  `sessionStorage`, refresh por cookie HttpOnly, interceptor axios para `/api/admin-auth/refresh`.
- **Vistas:** `AdminLoginView.vue`, `AdminLayout.vue` (panel), `AdminNegociosView.vue`
  (tabla con buscar/filtrar + acciones suspender/reactivar), opcional `AdminMetricasView.vue`.
- **Router:** rutas `/admin/login` y `/admin/**` con guard `meta.requiereAdmin`.
- **Separación:** la consola admin NO se mezcla con el panel del dueño (`/panel/**`) ni con el
  área de cliente. La PWA instalable sigue siendo solo `/panel/**` (no instalar la consola admin).

## §9 Pruebas

- `AdminAuthServiceTest`: login ok/credenciales inválidas, refresh con rotación, reuso de token
  revoca familia, logout revoca.
- `AdminTenantServiceTest`: suspender mueve estado y quema sesiones; reactivar restaura;
  un dueño de tenant suspendido no puede loguear (ya cubierto por `verificarTenantOperativo`,
  añadir el caso de borde).
- `AdminControllerIT` (Testcontainers): `/api/admin/**` con token DUENO/CLIENTE → 403;
  sin token → 401; con token ADMIN → 200. Bootstrap crea admin desde env.
- Negativos de seguridad: token ADMIN **no** puede tocar `/api/**` de negocio (no tiene tenant)
  ni `/api/cliente/**`.

## §10 Plan de implementación por fases

1. **F1 — Backend núcleo:** V18, `Administrador`+`RefreshTokenAdmin` (entidades/repos),
   `JwtService.emitirAccessTokenAdmin` + `TokenPort`, `AdminBootstrap`, `SecurityConfig`,
   `RateLimitFilter`, `AdminAuthService` + `AdminAuthController`. Tests de auth.
2. **F2 — Gobierno de negocios:** `AdminService` + `AdminController` (listar/suspender/reactivar),
   revocación de sesiones del tenant. Tests + IT.
3. **F3 — Frontend:** store + login + panel + tabla de negocios con acciones.
4. **F4 — (opción B) Métricas globales:** endpoint + vista de KPIs.
5. **F5 — Endurecimiento:** `admin_audit_log`, alta admin→admin, rate limit estricto.

Cada fase es un commit lógico vía gitflow (`feature/rol-admin` → `produccion` → `main`).
